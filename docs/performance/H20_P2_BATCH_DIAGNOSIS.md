# H20 / E5：P2 batch 对照与 CPU/CUDA 瓶颈实测

2026-11-13。按 [H20 batch 分析方案](../H20_BATCHSIZE_ANALYSIS.md) 执行。**B2A2 吞吐只比 B1A4 高 2.20%；主要瓶颈是串行 CPU 接触几何查询，第二个明确热点是 GPU 的 indexing backward。保留正式 B1A4，不继续扫描 B4。**

本次测量使用实际部署的 P2 源码 `e73d62e`，对应已发布 P2 源码快照 `4e9c9f5`，不是后来提交的 P3。执行前让 E5 正常保存暂停，使用同一张空闲 H20 完成测试，结束后恢复原学习状态；没有把测试样本计入正式训练预算。

**首要瓶颈已确认：CPU 查询与 GPU 计算基本串行。** 四个最长 CUDA 空档为 1.436、1.332、1.232、1.144 秒，对应逐帧 query。基准里 query 约占平均 wall 的 58%；增大 batch 没有减少每四帧所需的这些查询。多给数据加载 worker 或增大 Torch CPU threads，不会自动把这里的逐候选循环并行化。

**GPU 上也有明确热点：`indexing_backward_kernel<float, 4>`。** 431 次调用累计约 1.513 秒，占 kernel 区间并集约 64%。其中 54 次超过 1 毫秒的调用合计 1.4676 秒，占该变体时间约 97%。通过 External ID、`IndexBackward0` 的序列号与前向 `aten::index` 对应关系，这 54 次均落在 `encode_scene` 的 `fuse` 区域。结合源码，具体表达式推断为 `instance_blocks` 中 `stats['instance_features'][slots]` 的逐点实例特征广播及其反向累加；没有采集 Python stack，因此表达式级归属是源码支持的推断。不是四次 voxel-to-point gather，也不是区域索引主导了这个热点。仅凭时长还不能断言带宽、原子操作或计算饱和。

**固定 chunk 的调用数量确实存在，但目前优先级低于 CPU query。** 四帧中 dense fusion、q0、axis 各 54 个块，接触 local projection 16 个块，五区编码合计 320 个块。区域 point MLP 实际执行 320 次，其中 256 次形状 `[32,32,71]`、64 次 `[32,64,71]`。五区 chunk 的 host 区间合计约 0.313 秒，远小于 query。调用多并不自动证明 launch 开销是第一瓶颈。

时间线按流合并区间避免重叠重复计数；CPU 的嵌套 scope 与 GPU annotation 镜像分别处理。记录到的 CUDA 工作覆盖约 24.95% 的事件跨度，这是该诊断进程的时间线比例，不是硬件算力利用率。24 次 `cudaMemcpy` 的 host 调用耗时合计 1.214 秒，而实际设备复制/清零总共只有 0.016 秒，说明不能把同步等待误报为搬运时间。

## 显存上限为何没有造成这次瓶颈

112 GiB 是分配器上限，不是把剩余显存分给了别人，也不是必须用满的目标。本次 B2 reserved 峰值仅 34.46 GiB，距上限还有约 77.54 GiB；提高上限无法消除这次约 5.14 秒的串行 CPU 查询。

过去采用约八成物理容量，是为 CUDA 上下文、非 PyTorch 分配及不同输入的峰值留余量；**八成不是固定标准**。后续若更大的真实算子块或 batch 接近 cap，应依据 allocator 峰值、NVML 占用和输入波动重新设定余量，区分 cap 导致的 OOM 与物理显存不足。不能因 cap 偏低就认定显卡装不下，也不该按显存占用比例推算算力利用率。

## 后续优先级

1. 优先验证融合/并行 CPU 区域筛选、FPS 衔接及打包。GitHub 后续已有 [P3 实现](../PERFORMANCE_PHASE3.md)，方向与此次实测吻合；其本地 CPU 倍率还不是 H20 整步收益，本次没有部署或测量 P3。
2. 优先检查实例特征广播的 indexing backward，评估等价的分组梯度归约，保持学习状态及梯度语义，完成必要数值验证后再看整步耗时。
3. CPU query 缩短后再复测 batch 或 chunk；不以当前 P2 的 2.2% 结果推断所有未来版本都不受益。

正式 E5 已从暂停检查点恢复，预算仍为 230,400 有效帧，batch 保持 B1A4。此次没有新增验证节点、训练预算或质量结论。
