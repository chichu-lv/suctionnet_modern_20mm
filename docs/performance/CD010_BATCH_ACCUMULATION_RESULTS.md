# CD-010 batch 与梯度累积组合补测结果

按 [BATCH_ACCUMULATION_SUPPLEMENT.md](../BATCH_ACCUMULATION_SUPPLEMENT.md) 执行 H20/E5 与 L20/E3 各六档。全部使用 zone gather、pose chunk128、geometry pipeline depth2。

记录日期：2026-11-13（北京时间）。十二档均完整结束，合计3,456有效样本，其中2,880帧计时；全部计时窗口0 skip、梯度有限，无OOM，两个补测入口均exit0。

## 1. 结果与当前训练

- **H20**：完整历史组合加 zone128（`b4_a6_e24_zone128`）为 **2.750321 帧/s**，相对本轮现行配置 **+12.03%**。总体最快为 `b4_a12_e48_zone128`，**2.887176 帧/s**；有效 batch24 组最快为 `b3_a8_e24_zone128`。
- **L20**：完整历史组合加 zone128（`b1_a12_e12_zone128`）为 **3.700548 帧/s**，相对本轮现行配置 **+4.54%**。总体最快为 `b1_a12_e12_zone128`，**3.700548 帧/s**；有效 batch24 组最快为 `b1_a24_e24_zone128`。

补测结果没有自动替换正式训练配方。H20/E5 仍为 B4A2，L20 各正式组仍为 B1A8，有效 batch8、230,400 样本、28,800 次成功更新。

## 4. 相同有效 batch24 的分组比较

- **H20**：B3A8（2.779898 帧/s） > B4A6（2.750321 帧/s） > B2A12（2.595132 帧/s）。
- **L20**：B1A24（3.683097 帧/s） > B3A8（3.607115 帧/s） > B2A12（3.463453 帧/s）。

H20 B3A8仅比B4A6快1.08%，属于本轮短窗口的观测排序，不据此宣称稳定胜出。

总体排名改变了optimizer更新频率；同有效batch组固定了更新频率，但microbatch分组仍可能改变训练期BN及损失归约行为。单轮240帧窗口不能证明收敛、数学等价或微小差异的统计显著性。

固定B增加A时，每帧optimizer开销和暴露出的future等待通常减小，符合累积窗口减少更新边界开销的预期；但端到端吞吐仍取决于前向/反向、几何重叠与共享主机调度。L20从A12继续增加到A24/A48没有带来更高吞吐，不能由等待下降推定整体持续提速。optimizer本身只占每帧很小的时间，本轮没有kernel级trace，不能将全部收益归于optimizer或单一阶段。

L20 B2A12的loader等待中位数折合16.339毫秒/帧，明显高于同有效batch的B1A24（0.449毫秒/帧）和B3A8（0.136毫秒/帧）。B2本轮吞吐落后包含显著数据等待，因此不能单凭此结果断言GPU计算能力或显存带宽使B2必然更慢。未追加worker扫描或复跑以分离原因。

固定microbatch时，累积增加没有成倍增加在途显存：H20 B4的allocated峰值88.65→89.08 GiB；L20 B1约11.55–11.56 GiB。增大microbatch则明显增加allocated：L20 B2约22.43 GiB、B3约32.67 GiB；H20 B2约45.66 GiB、B3约67.17 GiB。

完整每更新median/p95、allocated/reserved峰值、有限梯度标记、skip与退出记录保存在各机summary.json及updates.jsonl。设备级低频资源快照另存私有原始记录；不是全时段采样，也不是trainer独占CPU/RAM核算。本轮未增加trace、worker/CPU/allocator扫描、完整验证或复跑。
