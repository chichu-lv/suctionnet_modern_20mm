# Route A CPU geometry for one training GPU

The fixed 12-channel sparse backbone and heads still receive one instance at a time. A source worker can prepare the final augmented observation using `model.prepare_source_geometry(observation)`. This computes the support selection, nearest-neighbor associations, deterministic contact rings, local descriptors and raw lip summary in CPU memory. The consumer computes the learned features on the GPU. Independent instances can overlap on separate CPU threads while retaining their scheduled order. Off-grid calls use their supplied pose coordinates. The prepared arrays are transient and belong only to the current observation and augmentation.

Build the optional existing native extension in the intended checkout using `python setup.py build_ext --inplace`. Route A then uses its FP64 loop with stable source-ID tie ordering for backbone and contact-zone sampling. Three-dimensional coordinate order is chosen to match the active NumPy einsum rounding on close ties. A checkout without the extension retains the original NumPy loop. This needs no new trainable parameter or checkpoint migration.

On two real source frames (scenes 0 and 44, first eight instances in each), all 6,160 calls returned the same index sequence using the final native and NumPy implementations. The 16 observations had 6,923–143,048 support points. Training queries used the 128-query prefix. CPU tests compared prepared and direct inference outputs and gradients, a noncanonical pose, duplicate coordinates and a one-ULP distance tie.

The isolated CPU preparation measurement used Python 3.10, NumPy 1.26.4 and a Xeon Gold 6530 host with the source data over SSHFS and one OpenMP/OpenBLAS thread per worker. Reading source NPZs, augmenting and preparing these 16 instances took 12.34 s serially and 5.50 s with four threads. Four processes took 3.71 s and eight processes took 2.62 s when returning only small statistics. Those process measurements omit transfer of prepared observations. These timings depend on OS file cache and sample order. They do not measure GPU update throughput.

An earlier bounded diagnostic on the same samples measured a single L20 training update. With the NumPy loop it took 21.26 s, of which 15.42 s was forward and 8.14 s in FPS. An experimental FP64 native loop took 8.83 s for the forward phase and 1.50 s for FPS. Total time including reads was 13.80 s. The second run benefited from faster reads. The final code additionally matches NumPy rounding and supports workers. These L20 observations are separate from the formal H20 runs.

For a new single-GPU configuration, compare serial loading, four and eight CPU workers using the same source draws and successful update count. In a checkout with the shared ordered training loader, the worker count is selected with `SUCTION20_INSTANCE_TRAIN_WORKERS`. Account for in-flight prepared observations when allocating host RAM.
